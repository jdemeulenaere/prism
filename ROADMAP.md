# Prism Roadmap & Milestones

Following the **Elephant-Goldfish model** via OpenSpec, this roadmap represents the high-level milestone tracking memory. Each phase is broken down into small, verifiable, test-driven work packets in `openspec/changes/`.

- [`openspec/specs/`](openspec/specs) describes only what is **implemented**.
- [`docs/architecture.md`](docs/architecture.md) describes what is **planned** for the unchecked items below. A change that implements a planned item moves its requirements from there into the specs.

### Next up: the road to the borrow checker
Agreed with the user in an `/opsx:explore` session (2026-10-17). Each item is one OpenSpec change, in this order; the decisions behind them are in [`docs/architecture.md`](docs/architecture.md) §1 (pipeline) and §3 (memory model).

1. [x] `statements-and-loops`: a `Statement` AST type (`Block` with an explicit tail expression, assignment as a statement); `while`, `do`/`while`, `for (x in range)` over the built-in `Range`; `break`/`continue` as `Nothing`-typed expressions with `E4015` outside a loop; the `..<` half-open range operator.
2. [x] `value-semantics`: opt-in `: Copy` and `: Clone` markers on structs and enums, checked structurally and recorded in the ABI; the built-in `Copy` and `Clone` tables (`String` is `Clone` but move-only); a built-in `x.clone()`; a move's source must be a whole owned local (`E4017`); top-level `var` removed.
3. [x] `reference-access`: implicit shared borrow at argument sites (temporaries included); implicit copy-out of `Copy` values from borrows, and moving out of a borrow rejected; prefix `*` for writing through a reference (`*r = v`); `var` reference bindings can be re-pointed; passing a `&mut` binding reborrows it. Moving out of a borrow extends `E4017` with the source "borrow" rather than taking a new code, and borrowing a nullable's contents without cloning (`&(T?)` to `(&T)?`) needs a design (both from `value-semantics`).
4. [x] `extension-methods`: methods are extension functions only, declarable in any file, with `fun` / `mut fun` / `consuming fun` receiver modes, implicit `this` and static dispatch; receivers borrow implicitly at the call site. A field takes precedence over an extension of the same name, as a field named `clone` does over the built-in `clone()`, and a user extension named `clone` on a `Clone` type is rejected (from `value-semantics`).
5. [x] `typed-tree`: a `prism-typed-tree` crate produced by the type checker, with resolved bindings, a type on every node, normalized calls and explicit copy/move/borrow adjustments, including the receiver adjustments `extension-methods` decides (`ReceiverAdjustment`); no behavior change.
6. [x] `mir-lowering`: a `prism-mir` crate lowering the typed tree of each file that typechecks to a place-based control-flow graph, with explicit storage, drops and branches, a `prism dump-mir <file.prism>` text format for snapshot tests, and a MIR validator. It decided where temporaries live (temporary scopes, with `val r = &make()` extending its temporary to the binding), how a default value runs (a generator body over borrows of the earlier arguments, with a caller-owned slot for a default that borrows a temporary), and how a `(&mut T)?` lent as `(&T)?` is reborrowed (a tag test and a shared reborrow of the payload).
7. [x] `borrowck-moves`: a `prism-borrowck` crate checking each file's MIR alone, and the `E5xxx` code range; use after move (`E5001`), including conditional and loop moves, consuming receivers and closure captures, reinitialization by assignment, and reads of uninitialized values (`E5002`), with diagnostics showing where the value moved. It also took drop elaboration from step 16: after a file passes, each drop is removed, kept or guarded by a drop flag (`prism dump-mir --elaborated`). By-value receivers are now evaluated before the arguments, and a default value may not move an earlier parameter (`E4017`).
8. [x] `borrowck-exclusivity`: non-lexical borrows from a loan flow and liveness on elaborated MIR, with `E5003` to `E5006` for conflicting borrows and reads, assignments and moves of borrowed values, and values that end while borrowed; disjoint field paths; two-phase receiver borrows by evaluation order (a safe call's receiver is borrowed at its test); call results that keep their input borrows (the caller's half of elision); closures capture by inferred borrow, with the modes recorded in elaborated MIR, may not move a capture (`E4017`), and a capturing closure or function-typed parameter cannot escape (`E5007`). Borrowed temporaries in branch values now live as long as the value, and block-end drops carry the closing brace's span.
9. [x] `borrowck-elision`: elision rules 1–4 derived from signatures alone, for callers (rule 2 now keeps only the receiver borrowed) and callees (`E5008` `DanglingBorrowReturn` for a returned borrow of a local, temporary or by-value parameter, `E5009` `UntiedBorrowReturn` for one derived from an input the rule does not tie the result to); function types elide by the same rules, so a closure whose type takes a borrowed input cannot return its captures; defaults borrow only through shared references; borrows of top-level `val`s are valid everywhere; by-value parameters end at each return; and a `(&mut T)?` lent as a `(&mut T)?` is reborrowed.

### Then: the road to Milestone 2
Planned autonomously on 2026-10-17, when the user asked for iteration up to Milestone 2 (see [`docs/decisions-for-review.md`](docs/decisions-for-review.md)). Each item is one OpenSpec change, in this order; the order and scope may be revised as changes land, and any revision is logged there.

Needed for `State<T>`. Monomorphization was split out into its own change, now item 19 (2026-10-18). Also: one extension per receiver constructor (`E4010`), the new codes `E4020` to `E4022`, generic default value generators, MIR aggregates with type arguments, and expected types reaching `?:` fallbacks and borrowed arguments (from the review).

[x] `abi-cache`: BLAKE3 at 256 bits for every hash, a per-file interface hash, a per-user content-addressed build cache (`PRISM_CACHE`, `--no-cache`, `--explain-cache`) through which `prism check` skips Phase 2 for files whose content and imports' interfaces were already checked, and instance records standing in for re-monomorphization; the avoidance scenarios run as CLI tests ([`build-cache`](openspec/specs/build-cache/spec.md)). From the review, instance keys also cover the generic's signature. `.abi` entries were deferred (below).
13. [x] `prism-fmt`: the `prism fmt` code formatter ([`formatting`](openspec/specs/formatting/spec.md)): a `prism-formatter` crate printing the AST through a width-aware document algebra in the Kotlin conventions, comments from a comment-collecting lexer mode, written forms the tree does not record read back from the tokens, and a check on every run that the output parses to the same tree with the same comments; `prism fmt [--check] <path>...` and `-`, with no options; `examples/` formatted. From the review, comments before a block's `{` move inside it and line comments inside expressions indent what follows them. Follow-ups are in Phase 1 above.
14. [x] `codegen-core` (Phase 3): a `prism-codegen` crate lowering elaborated MIR to Cranelift, one code unit per file, every call through a patchable function table; a `prism-runtime` crate; `prism run` for `Int`/`Double`/`Bool`/`Char`, functions across files, control flow, loops, top-level `val`s (initialized on first read) and references to scalars; `print`/`println` built-ins; overflow and division by zero as runtime errors (exit status 101); `E6001` for constructs the backend does not support yet, `E6002`/`E6003` for `main`; an executable-fixture runner comparing stdout and stderr. Generic bodies wait for `monomorphization`. References to scalars moved here from item 15 (proposal of `codegen-core`, D8). From the review, a stack overflow is the runtime error "stack overflow" (status 101, output kept) rather than an abort, and a subnormal `Double` prints as Kotlin does (`4.9E-324`). Follow-ups are in Phase 3 below ([`code-generation`](openspec/specs/code-generation/spec.md), [`execution`](openspec/specs/execution/spec.md)).
15. [x] `codegen-aggregates`: structs, enums, nullables, references to them and `when` over them in the backend, and the layouts of types from transitively imported modules. References to scalars already landed in `codegen-core` (D8). Done: deterministic layouts (structs inline with fields by decreasing alignment, enums as the smallest tag then payloads, `T?` as a tag byte or, for `(&T)?`, `(&mut T)?` and `Heap<T>?`, a null pointer), concrete instances of generic types, aggregates passed by address and returned through a caller address, structural `==`, `?.`/`?:`, `clone()` and drops of values that own nothing, `Range` as an ordinary struct, aggregate top-level values, `prism dump-layout` with `layout.snap` fixtures, the ABI's reachable type definitions (so a layout change re-checks exactly the affected importers), and `E4023` for infinitely sized types. Aggregates holding a `String` or a `Heap<T>` stay `E6001`. From the review, reachable definitions serve layout only: the members of a private type reached through an import stay hidden ([`code-generation`](openspec/specs/code-generation/spec.md), [`execution`](openspec/specs/execution/spec.md)).
16. [x] `runtime-strings-and-drops`: owned `String` (UTF-8, a pointer, byte and character lengths and a capacity; literals as static data), concatenation, equality, `length`, character indexing and printing; `toString()` of the scalar types; an allocator in `prism-runtime`; drop glue (what dropping a `String`, a struct, an enum or a nullable does, at every drop the elaborated MIR keeps) and clone glue, generated per code unit; `prism run --check-allocations`, with which every executable fixture checks that nothing leaks or is freed twice. Drop elaboration on MIR was done by `borrowck-moves`. `s += t` may append in place instead of building a new string, which the semantics allow (from `compound-assignment`, D3); the proposal keeps it a concatenation (D15). `Heap<T>` and string templates were split out into items 18 and 19 (proposal of `runtime-strings-and-drops`, D1). Done: `length` and `s[i]` count Unicode scalar values (D4), a string's character is a value rather than a place, so `&s[i]` borrows a temporary (D5), the built-in members win over extensions (`E4010` for those never callable), top-level values are never dropped but released by the check before it reports (D12), invalid frees and leaks end the run with status 102, and the runtime errors "string index out of range" and "out of memory". From the review, end-to-end tests show the check catching a leak of compiled code and, in a child process, a double free ([`code-generation`](openspec/specs/code-generation/spec.md), [`execution`](openspec/specs/execution/spec.md)). Follow-ups are in Phase 3 below.
17. [x] `payload-patterns`: patterns that mirror construction in `when` branches (`Shape.Circle(val r)`, `Point(y = val y)`, nested sub-patterns, `_`, `val`/`var` bindings, values and ranges), a payload variant named alone (`Shape.Circle`), Kotlin 2.1 guards (`pattern if condition ->`), alternatives that bind alike (`E4025`), binding modes from the subject's type (owned by value, `&E` borrowing, `&mut E` borrowing mutably, so `when (this)` follows the receiver mode), and destructuring declarations by field name (`val (name, email) = user`, `val (name as n) = u`). Taking a value apart moves it whole (`E4017` for fields, borrows and top-level values; `E5001` after it, labelled at the binding), and the parts no binding takes are dropped where the branch ends, so partial moves stay out of the language (D7). Exhaustiveness and usefulness by Maranget's algorithm, with a missing value named in `E4009`; `E4024` for patterns that do not fit their subject. MIR gains variant-payload places and `Destructure`. From the review, a binding of the whole owned subject is assigned, a guard cannot change a subject its pattern takes apart (a shared borrow of the subject across the guard), imported structs can be matched, and taking apart through `?.` suggests the right borrow ([`patterns`](openspec/specs/patterns/spec.md)). Follow-ups are in "Follow-ups of `payload-patterns`" below.
18. [x] `heap-boxes`: `Heap<T>` values. `Heap(value)` boxes a value (`Heap<Int?>(1)` names the contents; `Heap` is a built-in constructor, `E4010` for a declaration of that name). A box reads like a reference to its contents (operators, conditions, copy-out, output, `toString()`, fields and receivers), an owned box lends its contents to `&T` and `(&T)?` parameters, and borrowed boxes convert to borrowed contents (D21). `*h = v` writes a mutable box's contents, one layer per `*`. `h.unbox()` moves the contents out and frees the box, and a `consuming fun` receiver reached through boxes is unboxed (`E4017` before). Boxes are invariant (D8). Patterns look through boxes, and taking apart through a box unboxes it. The backend allocates exactly sized boxes (none for zero-sized contents), with drop, clone and `#equals` glue, and every glue function checks the stack, so a too-deep structure is "stack overflow". From the review, branch and `?:` operands are consumed (a MIR crash before) and patterns match the referent of a `(&T)?` subject ([`references`](openspec/specs/references/spec.md), [`code-generation`](openspec/specs/code-generation/spec.md)). Follow-ups are in "Follow-ups of `heap-boxes`" below.
19. [x] `string-templates`: Kotlin line string templates, `"Count: $count"` and `"${a + b}"`, with `\$` for a dollar sign and `$` literal before anything but an identifier or `{` (`$` followed by a keyword other than `this` is `E2001`). The lexer emits a flat token run with a mode stack, an expression part holds any expression (nested templates, closures, `when`, comments, newlines), and `"$x"` and `"${x}"` give the same tree. A part is read in place through references and boxes and never moved: a `String` as it is, a scalar as `print` writes it, any other type through the `toString()` that `.toString()` resolves, which must take a shared receiver, need no arguments and return `String`; nullable, `Unit`, function and type-parameter parts are `E4026`, whose help names the fix (`${n ?: ...}`, `fun User.toString(): String`, `${u.name}`, `${c.toString()}`) (D6 to D8). MIR's `Rvalue::Template` evaluates parts left to right, borrowing string parts until the result is built (`E5003` for a later `&mut`), and the backend makes one runtime call over a part table in a stack slot, allocating the result once with exactly its length. `prism fmt` keeps text and parts as written, formats each `${}` flat and never breaks a template, keeping one with a comment or a multi-line part verbatim on the line of its `=` (D14, D16). From the review, the `E4026` helps parenthesize a part that binds less tightly than `?:` and `.` ([`syntax`](openspec/specs/syntax/spec.md), [`type-system`](openspec/specs/type-system/spec.md), [`code-generation`](openspec/specs/code-generation/spec.md)). Follow-ups are in "Follow-ups of `string-templates`" below.
20. [x] `monomorphization`: generic code runs in Tier 1. Each generic function, extension and default value is instantiated per concrete type argument list over the whole program, transitively and across files, into one code unit per instance with its own function-table slot (`lib/box::keep<Int>`), so no file's code depends on a generic body. Instances are built from per-generic records of elaborated polymorphic MIR (private generics included; non-generic helpers are called by symbol). Substitution resolves type-parameter drops and flattens `T?` with a nullable `T`, `?:` on a `T` tests for null as in Kotlin, and polymorphic recursion is `E4027` (per file) or `E6004` (across an import cycle). Adds `--instances` on `dump-mir` and `dump-clif`. Caching split out to item 21 (proposal of `monomorphization`, D1) ([`generics`](openspec/specs/generics/spec.md), [`mir`](openspec/specs/mir/spec.md), [`code-generation`](openspec/specs/code-generation/spec.md), [`compilation-and-abi`](openspec/specs/compilation-and-abi/spec.md), [`execution`](openspec/specs/execution/spec.md)). Follow-ups are in "Follow-ups of `monomorphization`" below.
21. [x] `instance-cache`: generic records carried in the defining file's check entries, the Monomorphization Hash moved from the Phase 1 AST hash onto the record (bodies with positions, used type definitions), the ABI hash merged with the interface hash, instance keys that also cover their type arguments' definitions, transitive instance records per program in `prism check` and `--explain-cache`, cross-file polymorphic recursion found by `prism check`, and re-monomorphization only where a generic record changed ([`docs/architecture.md`](docs/architecture.md) §1; `monomorphization`, D13). Needed before `hot-reload`. Proposed: generated code is cached too, per file unit and per instance unit as relocatable artifacts keyed with a target identity, so a warm `prism run` compiles nothing and `prism run` uses the cache by default; check entries hold per-file summaries and records are entries addressed by their Monomorphization Hash; `prism check` plans the program's instances and reports `E6004`, which stays (proposal of `instance-cache`, D1, D5, D7, D8). Done in `instance-cache` ([`build-cache`](openspec/specs/build-cache/spec.md), [`compilation-and-abi`](openspec/specs/compilation-and-abi/spec.md), [`code-generation`](openspec/specs/code-generation/spec.md), [`generics`](openspec/specs/generics/spec.md), [`execution`](openspec/specs/execution/spec.md)), as proposed: a warm `prism run` of `examples/run` takes 1.3 ms to `main` in a release build. From the review, the resolver reads each directory once (the warm front end grew 6.6x for 4x the files) and the executable's hash is recorded under its file metadata (D16). Follow-ups are in "Follow-ups of `instance-cache`" below.
22. [x] `closures`: closure conversion in the backend for today's closures. A function value is a descriptor address (the closure code's function-table slot and an environment drop entry) and an environment address; each closure's code is a function with its own slot (`main::f#closure0`); borrowing closures keep one pointer per capture in the creating frame and allocate nothing; function names and variant constructors as values are adapter closures in MIR; function values convert to other function types only without changing representation (BREAKING); closures of generic bodies run in their parent's instance. Escaping closures were split out into item 23 (proposal of `closures`, D1).
23. [x] `escaping-closures`: escaping closures that own their captures, needed by compose event handlers (`Button(onClick = { count.value += 1 })`) and by closures stored in values. Done: the type checker decides from the source, flow-insensitively and in one linear walk of each body with closures, which captures a closure owns (all of them when its value may reach an owning position, through locals, branches and `when` bindings; one it may outlive otherwise), recording the modes in the typed tree; an `escaping` marker on function-typed parameters that keep their value, part of function types (unmarked converts to `escaping`) and of the ABI hashes; `E4028` for owned captures of `var`s and of values the closure cannot take; `E5007` narrowed to escaping values that may hold a borrow; `E5008` for a borrow of an owned capture; owned environments in one exact-sized allocation freed by `<closure>#drop-environment` through the descriptor, held in the environment word when they fit one word and need no drop, so a handler capturing one `Copy` handle allocates nothing; owning closures in generic slots and boxes.
24. [x] `collections`: a built-in growable `List<T>`, needed for UI children and the todo-list app. Added on 2026-10-18 (process row P6). Done: `List<T>` is a structural built-in type with a reserved name (`E4010`, `E4001` as a value), invariant, `Clone` when its element is and an indirection for `E4023`; `listOf(...)` is a variadic built-in typed as a generic call of that many parameters, found last; `size`, `indices`, `isEmpty`, `isNotEmpty`, `contains`, `indexOf`, `add`, `insert`, `removeAt`, `removeLast`, `reverse` and `clear` are built-in extension records that win over extensions; `xs[i]` is a place, bounds-checked with a located runtime error; `for (x in xs)` borrows the list for the loop and binds `&T` (`&mut T` over `&mut xs`), with `Range` and `List` the two built-in iterables (no protocol before traits); element borrows borrow the list; `==`, `contains` and `indexOf` where `==` on the element is; a `{ pointer, size, capacity }` layout growing by doubling, inline fast paths, runtime slow paths and per-type drop, clone, equality and index-of glue. A million adds run in 4.2 ms. The higher-order helpers moved to item 26 (D1, D10, D17).
25. [x] `hot-reload`: `prism run --watch` defining a changed file's new code unit into a new JIT module and repointing its slots of the function table `codegen-core` built, and deciding what happens to the values of its top-level `val`s (`codegen-core`, D24). Old modules must stay mapped while the program runs, since a top-level value or slot-table state may point at a string literal's data in old code (`runtime-strings-and-drops`, D3). Proposed: the program thread applies a reload at its next call, through the stack-limit check every function entry makes (D3); slots record a contract of type fingerprints, and a changed contract gives the symbol a new slot while old code keeps the old one, so no reload is refused and no value is migrated (D5 to D7); top-level values are kept unless their type or initializer changed (D8); old modules stay mapped for the life of the program (D10); `--edits <script>` drives reloads deterministically for fixtures (D16); a 50 ms save-to-patch target (D17). A closure's slot may be repointed only while its environment layout is unchanged: values built before a reload keep their old drop function but would run new code on an old environment, so a closure whose captures changed needs a new slot, for every function value as `compose-hot-reload` plans for composables (`escaping-closures`, Risks). Done in `hot-reload` ([`hot-reload`](openspec/specs/hot-reload/spec.md), [`code-generation`](openspec/specs/code-generation/spec.md), [`execution`](openspec/specs/execution/spec.md)), as proposed: `prism run --watch` keeps the program running and patches it at its next call, every compiled body's stack check being a reload point; slots record contracts and split on a changed signature or changed captures, with a note on stderr; top-level storage lives in a program value table; a reload compiles only the units whose code key changed, through the build cache, and old modules stay mapped; `--edits` scripts drive the watch fixtures. A body edit in a 100-file program reaches the running program in a median of 31 ms on a release build (`reload_timing.rs`, D17). From the review, type fingerprints no longer depend on the order a unit computes them in (reordering declarations had split slots), the session watches the files a failed start reached and reads a file again when it rejoins the program, and a reload requested as a run ends is no longer applied to it. Follow-ups are in "Follow-ups of `hot-reload`" below.

[x] `standard-library` (Phase 4): Prism source packages bundled with the compiler under the reserved root package `prism` (`import /prism/ui`; a workspace package named `prism...` is rejected), covered by the compiler version; `external fun` (a runtime entry point called by symbol with the C calling convention) and `intrinsic` declarations (lowered by the compiler), both accepted only in bundled files; `/prism/compose` as a prelude in scope in every file.
