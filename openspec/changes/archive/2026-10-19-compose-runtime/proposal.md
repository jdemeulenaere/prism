# Proposal: compose-runtime

## Why

A `compose fun` parses, type-checks and lowers to MIR today, but nothing can run it: there is no composer, no slot table and no recomposition. The compose plan (`docs/architecture.md` §5, decided as `compose-architecture` D1 to D25) puts that machinery in a Rust crate, `prism-compose`. It knows nothing about UI, generated code reaches it only through `extern "C"` entry points, and it calls user code only through function values and drop entries. This change is item 27 of "Then: the road to Milestone 2" in `ROADMAP.md`, the first Phase 4 change after `standard-library`. It builds the runtime half of composition, which `compose-transform` (the compiler pass), `state-handles` (state cells) and `ui-toolkit` (the node tree) then build on. It also fixes the protocol between generated code and the runtime before any compiler code depends on it. That protocol is pinned by Rust tests and by executable Prism fixtures written by hand in the form the transform will generate.

## What Changes

- **A `prism-compose` crate** (D2). It depends on `prism-runtime` only, has a Rust API (`Composition`, `Applier`) for its tests and for `prism-ui`, and has a table of `extern "C"` entry points, `COMPOSE_FUNCTIONS`. The JIT resolves these entry points, and the backend checks externals against them (`E6005`) as it does for `RUNTIME_FUNCTIONS`.
- **Compositions and passes** (D4, D11). A composition owns a root content function, a tree of groups, an applier, an invalidation queue and the values its groups hold. Starting a composition composes its content once. Setting new content recomposes the root. Recomposing runs one pass over the invalid scopes and reports whether any ran. Disposing removes everything. A thread runs one pass at a time, so starting, recomposing, setting the content of or disposing any composition during a pass is a runtime error, and a scope invalidated during a pass is recomposed in the next one.
- **The slot table** (D5, D6, implementing `compose-architecture` D6). A generational arena of groups. Each group holds a key, a kind (restart, replaceable, movable, node), its parent, its ordered children, its slots, an optional node and, for restart groups, a restart function. Starting a group reuses the first unvisited old sibling with the same key, or with the same key and data key for movable groups. Equal keys match in order, and a group is created when nothing matches. At a group's end, its unvisited children are removed and its unvisited slots forgotten.
- **Type-erased slots** (D6). A slot holds a value with its size, alignment, drop entry, equality entry and type fingerprint, described by a static slot type record. A slot whose type does not match the record a caller asks for is discarded and recreated. That makes a wrong key match memory-safe, which hot reload relies on (`compose-architecture` D5, D23). Generated code reads, writes and compares slots through the record. The Prism-level protocol also has *word slots*, 64-bit values tagged by an `Int`, for hand-written code that cannot name a record.
- **Deferred removals** (D7). Removed groups, forgotten slots, replaced restart functions and replaced root content are released at the end of the pass, so every slot address and value handed out during a pass stays valid until the pass ends. Release order is children before parents, and within a group slots last to first, then its restart function, then its node.
- **Restart scopes and invalidation** (D8). A restart group keeps the restart function its last run passed, an owned `(Int) -> Unit` function value that the runtime calls with the pass's composer to recompose that group alone. Scope handles are generational, and invalidating one costs O(1). Invalidating a removed scope does nothing. A pass recomposes invalid scopes in tree order, parents first, each at most once, and drops scopes that their parent's recomposition removed. `skipping` and `skipToGroupEnd` let a body skip when its scope is valid. The runtime never interprets change words, which are `compose-transform`'s.
- **Node groups through an applier** (D9, implementing `compose-architecture` D7). A node group creates its node through the composition's `Applier` on its first pass and reuses it after. Nodes are placed and moved during composition in group order, and removed at the end of the pass. A composition created through the entry points uses a built-in *node tree* applier, which keeps kinds and children only. `ui-toolkit` supplies its own applier.
- **Handles and misuse** (D3, D12). A composer is the identifier of the pass in progress, and compositions, scopes and nodes are 64-bit generational handles, so every entry point validates its arguments in O(1). Misusing the protocol is a runtime error, `panic: composition misuse: <detail>` with status 101 and no location: a stale composition, a composer outside its pass, an unbalanced group, or a composition operation during a pass. It is never undefined behavior.
- **A Prism-level protocol module** (D10). A new bundled library module, `/prism/composer`, outside the prelude, declares every entry point that hand-written code can use as a `private external fun prism_compose_*`, with public wrappers over plain `Int` words (`startRestartGroup(composer, key)`, `rememberInt(composer, typeTag) { ... }`, `endRestartGroup(composer) { c -> Label(c, n) }`). Executable fixtures `import /prism/composer` and write composables as the transform will lower them, so the runtime's behavior is pinned by real `.prism` source before the transform exists.
- **Text dumps** (D14). `dumpComposition(composition)` returns the group tree, one group or slot per line, followed by the applier's node tree. Fixtures compare these dumps.
- **The allocation check counts compositions** (D13). Under `--check-allocations`, a composition still live when `main` returns is reported as `allocation check: compositions still live at exit: <n>`, with status 102.
- **Costs and benchmarks** (D16). Starting and ending groups and reading and writing slots cost O(1) amortized. A pass costs time proportional to the bodies of the scopes it recomposes, plus O(k log k · depth) to order k invalid scopes. Once its buffers have grown, a pass allocates nothing that the runtime itself owns. An allocation-counting test and an ignored timing benchmark, `runtime_timing.rs`, pin both. No compiler stage is added, so compile time does not change.
- **Not in scope.** All of the following belong to later changes:
  - the `compose fun` transform: group keys from declaration paths, change words, generated restart functions and slot type records, `remember` and `key`, `/prism/compose/runtime` and its owned `Composition` type (`compose-transform`);
  - state cells, readers, writes during composition and cell ownership (`state-handles`);
  - the UI applier, `Node` and the frame loop (`ui-toolkit`);
  - recomposing reloaded scopes (`compose-hot-reload`);
  - counting live groups, cells and nodes as leaks (`reactive-app-verification`);
  - subcompositions, nested passes, threads, and the effect APIs (`compose-architecture` D25).

## Capabilities

### New Capabilities
- `compose`: the composition runtime: compositions and passes, the slot table, group matching, slots and their types, deferred removals, restart scopes and invalidation, node groups and the applier, handle validation and misuse errors, the composer protocol module `/prism/composer`, dumps, and the runtime's costs. `compose-transform` and `state-handles` add the language side to this capability later.

### Modified Capabilities
- `execution`: "Runtime Errors End the Program" also writes no location for composition misuse, and a new requirement reports undisposed compositions under `--check-allocations`.
- `standard-library`: "The Compiler Ships the Library" lists `/prism/composer` among the bundled modules, outside the prelude.

## Impact

- New `crates/prism-compose`: `handle.rs`, `group.rs`, `slot.rs`, `composition.rs`, `composer.rs`, `applier.rs`, `thread.rs`, `dump.rs`, `entry.rs`, `functions.rs` and `test_support.rs`, plus the tests `tests/allocations.rs` and `tests/runtime_timing.rs`. It is a workspace member.
- `crates/prism-runtime`: `function_value.rs` (calling and dropping function values from Rust), `PanicKind::CompositionMisuse`, and a finish report hook in `allocation.rs`.
- `crates/prism-codegen`: depends on `prism-compose`. `link.rs` registers `COMPOSE_FUNCTIONS` with the JIT, `externals.rs::entry_point` looks entry points up in both tables (for the external check, external calls and runtime imports), and `program.rs` installs the composition report.
- `crates/prism-library`: `prism/composer.prism` and its module entry, not in `PRELUDE`.
- `crates/prism-cli`: fixtures under `tests/fixtures/compose/` and `tests/fixtures/execution/`. `library_tests.rs` covers the new module unchanged.
- Specs: the `compose` capability, and the `execution` and `standard-library` deltas. No error code is added. `docs/architecture.md` §5: the runtime halves of "Compose Runtime Crates Behind C Entry Points", "Slot Table of Groups and Owned Slots", "Restart Scopes and Invalidation", "Compositions Are Owned Values" and the node-change rule of "UI Node Tree Owned by the Runtime" move out on archive. The composer word of "Composable Calling Convention" is revised (D3).
- **Prerequisites:** `closures`, `escaping-closures` and `standard-library` are archived first, which also brings in `monomorphization`, `instance-cache`, `collections` and `hot-reload` (standard-library's baseline). The Rust core (task groups 1 to 6) needs only `closures`' function value layout and can start earlier. See `design.md`, "Baseline".
